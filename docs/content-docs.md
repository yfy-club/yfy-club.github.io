# 上手

## 1. 环境基线 · `env-baseline`

**摘要**：装这几个版本，别装别的。
**阅读**：3 分钟

### 版本

| | 版本 | 备注 |
|---|---|---|
| Node.js | 22 LTS | 低于 22 的构建会挂 |
| Java | 21 LTS（Temurin） | 不用 Oracle JDK，授权麻烦 |
| PostgreSQL | 17 | |
| Git | 2.40+ | |

### 起项目

```bash
npm ci                              # 不是 npm install
npx playwright install chromium     # 浏览器要单独装
npm run dev
```

`npm ci` 严格按 lockfile 装。`npm install` 会改 lockfile，改完你自己都不知道装了什么。

### 换行符

Windows 上先关掉自动转换，再靠仓库的 `.gitattributes` 统一成 LF：

```bash
git config --global core.autocrlf false
```

开了 `autocrlf=true` 的后果是每次提交整文件飘红，评审时看不出你到底改了哪一行。

### 环境变量

从 `.env.example` 复制成 `.env.local`。`.env.local` 已在 `.gitignore` 里，别去掉。

任何 Token、密钥、内网 IP、数据库口令不进源码、不进 Markdown、不进截图、不进日志。

## 2. 第一周 · `first-week`

**摘要**：七天里该完成的事，按顺序。
**阅读**：2 分钟

### 前三天

跑起来一个项目，随便哪个。跑不起来就在群里贴完整报错，别贴"我这边有问题"。

读那个项目的 `README` 和 `CONTRIBUTING`，不用读懂全部，知道哪个目录放什么就行。

### 第四到第五天

领一个标了 `good first issue` 的活。第一个 PR 控制在 50 行以内。

改之前先在 issue 下说一句你打算怎么改。方案错了，早说早改，比写完再推翻省事。

### 第六到第七天

给你改过的那块代码补一条测试。哪怕只测一个分支。

跑一遍完整门禁，绿了再发 PR：

```bash
npm run typecheck && npm run lint && npm run test && npm run build
```

### 三条前提

问问题前先搜一遍仓库和历史 issue。搜过没有再问，并说明你搜了什么。

不确定的地方直接说不确定。猜着写然后让评审去发现，浪费两个人的时间。

代码是要被别人读的。名字取长一点没关系，取错了才有关系。

# 约定

## 3. 分支与提交 · `git-flow`

**摘要**：分支怎么起名，提交怎么写，PR 怎么开。
**阅读**：3 分钟

### 分支

```
feat/<简短英文>      新功能
fix/<简短英文>       缺陷
chore/<简短英文>     构建、依赖、配置
docs/<简短英文>      文档
```

从 `main` 切出，改完开 PR 回 `main`。不直接往 `main` 推。

### 提交信息

Conventional Commits，中文正文：

```
feat(join): 报名表单增加方向多选校验
fix(monitor): 修正遥测断线后 SSE 不重连
```

主语写"改了什么"，不写"修改了一些问题"。一次提交只做一件事。

### PR

标题同提交格式。正文写三行：改了什么、为什么、怎么验证的。

截图只在改了界面时放。放之前确认里面没有真实姓名、学号、内网地址。

### 禁止

不 force push 到共享分支。
不在自己的 PR 里顺手格式化无关文件。
不合并没跑过门禁的 PR。

## 4. 前端约定 · `frontend`

**摘要**：TypeScript、目录、状态、样式。
**阅读**：4 分钟

### TypeScript

`strict: true`，不关。

不用 `any`。类型实在推不出来用 `unknown` 再收窄。给 `any` 的地方写清楚为什么，写不清楚就说明还没想明白。

对外暴露的函数写显式返回类型。内部函数交给推导。

### 目录

```
src/
  components/    可复用组件，不含业务数据
  sections/      页面区块，可以含业务数据
  data/          静态内容，单一真源
  lib/           纯函数工具，不碰 DOM
  styles/        令牌与全局样式
```

同一份事实只存在于一个文件。需要在第二处用到就 import，不复制。

### 状态

能用 props 传的不提到 store。能用 URL 表达的不放内存——筛选条件、当前页、展开项一律进 query string，刷新后要还在。

跨三层以上才考虑 context。全局 store 只放真正全局的东西（当前用户、主题、语言）。

### 样式

颜色、间距、圆角、时长一律从 CSS 变量取。组件里不写 `#hex`，不写魔法数字。

```css
/* 不要 */
color: #2E9BE0;
padding: 13px;

/* 要 */
color: var(--sky-500);
padding: var(--space-3);
```

改一个颜色要改十个文件，说明令牌层没建好。

### 动效

只动 `transform` 和 `opacity`。动 `width`、`height`、`top`、`left` 会触发布局，掉帧。

`prefers-reduced-motion: reduce` 下必须能关。这不是可选项。

## 5. 后端约定 · `backend`

**摘要**：分层、事务、错误、迁移。
**阅读**：4 分钟

### 分层

```
controller   只做参数校验与响应组装，不写业务
service      业务逻辑与事务边界
mapper       只做数据访问
```

Controller 不注入 Mapper。想跳层说明 Service 该拆了。

### 事务

`@Transactional` 加在 Service 方法上，不加在 Controller 上。

事务里不发 HTTP 请求、不发消息、不写文件。这些做完再做，或者交给事务提交后的回调。事务持有连接的时间越长，池子越容易干。

只读查询标 `@Transactional(readOnly = true)`。

### 错误

业务异常用自定义异常带错误码，统一异常处理器转响应体。不在 Controller 里写 try-catch 拼错误 JSON。

返回给前端的错误信息要能让用户看懂并知道下一步做什么。堆栈进日志，不进响应体。

### 数据库迁移

结构改动一律走 Flyway，一次改动一个版本文件。

已合并的迁移文件不改。改错了就再加一个版本修回来。

字段加 `NOT NULL` 时先给默认值，再分两次上线。一步到位会锁表。

### 日志

日志里不出现口令、Token、身份证、手机号。手机号要打印就脱敏成 `138****1234`。

`INFO` 记录状态流转，`DEBUG` 记录中间值，`ERROR` 只在真的需要人来处理时用。满屏 `ERROR` 等于没有 `ERROR`。

## 6. 接口契约 · `api-contract`

**摘要**：后端定 OpenAPI，前端生成客户端，中间不手写。
**阅读**：3 分钟

### 流程

后端写完接口导出 OpenAPI，前端用 Orval 生成类型与请求函数。生成产物提交进仓库，但**不手改**。

```bash
npm run api:generate
```

改了接口没重新生成，前端一定在某个地方悄悄错。类型对不上就是提醒你该跑这条命令了。

### 响应结构

统一包一层，前端只需要处理一种形状：

```ts
interface ApiResponse<T> {
  code: number
  message: string
  data: T
}
```

`code` 为 0 表示成功。HTTP 状态码表达传输层结果，`code` 表达业务结果，两者不混用。

### 分页

```ts
interface Page<T> {
  items: T[]
  total: number
  page: number
  size: number
}
```

`page` 从 1 开始。`size` 上限 100，后端强制截断，不信任前端传值。

### 破坏性变更

改字段名、改类型、删字段都是破坏性变更。先加新字段，前端切完，再删旧的，分两次上线。

# 质量

## 7. 测什么 · `testing`

**摘要**：哪些必须有测试，哪些不必浪费时间。
**阅读**：3 分钟

### 必须测

算钱的、算分的、判权限的。
状态机的每一次流转。
解析外部输入的函数——表单、上传、URL 参数。
修过的缺陷。修完补一条能复现它的测试，否则它会回来。

### 不必测

框架本身的行为。
纯转发、没有分支的一行函数。
第三方库的返回值。

覆盖率是体检指标，不是目标。为了数字去测 getter，只会让人不敢改代码。

### 单元测试

一个测试测一件事。测试名写清楚"什么情况下应该怎样"：

```ts
it('阶数超过 8 时拒绝计算并给出提示', () => { ... })
```

不写 `it('test1')`。三个月后没人知道 `test1` 在测什么。

不 mock 被测对象自己。mock 到处都是，说明依赖太多，该拆。

### 端到端测试

只覆盖主干路径。E2E 慢且脆，写多了没人愿意跑。

不用真实学生信息做测试数据。

### 门禁

发 PR 前本地跑一遍：

```bash
npm run typecheck && npm run lint && npm run test
```

红的不发。CI 不是你的本地环境。

## 8. 评审 · `review`

**摘要**：看四件事，其余的交给工具。
**阅读**：2 分钟

### 只看四件事

**能不能跑对**——边界值、空值、并发、失败路径有没有处理。

**会不会伤到别人**——改的是不是公共接口，有没有人在用。

**三个月后读不读得懂**——命名、拆分、注释解释的是"为什么"还是"是什么"。注释重复代码是噪音。

**该不该在这一层**——业务逻辑跑进了组件里，SQL 拼进了 Controller 里，现在不说以后没人会说。

### 交给工具

缩进、引号、分号、import 顺序、行尾空格。这些 ESLint 和 Prettier 会管，评审时提等于浪费两个人的时间。

### 怎么说

提问题给出理由，最好给出改法：

```
这里 findById 可能返回 null，第 42 行直接 .name 会炸。
建议先判空返回业务异常。
```

不写"这样写不好"。不好在哪，对方不知道。

区分"必须改"和"建议改"，明确标出来。全是"建议"会让人不知道哪些不改就不能合。

### 作者这边

被指出问题不用道歉，改了回一句"已改，见 xxx"就行。

不同意就说不同意，把理由讲清楚。评审是讨论，不是审判。
