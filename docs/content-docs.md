# 上手

## 1. 递进路线 · `training-roadmap`

**摘要**：从基础语法启蒙到综合工程落地的演进过程。
**阅读**：4 分钟

### 阶段一：语法启蒙与算法基础

从 C 语言建立程序逻辑与内存控制意识，掌握流程控制、指针运算与内存分配机制。

进阶至 C++ 学习面向对象编程思想与标准模板库，重点训练链表、栈、队列与树等常用数据结构，通过算法训练提升逻辑建模能力。

### 阶段二：Web 前端基础

学习 HTML5 语义化标签与页面文档结构，掌握 CSS 盒子模型与弹性布局（Flexbox / Grid），实现多端视口适配。

通过 JavaScript 理解文档对象模型操作、事件驱动机制与异步处理，掌握现代 Web 交互逻辑。

### 阶段三：技术方向专项分流

依据工程兴趣与技术路径进入专项学习：

| 方向 | 核心技术栈 | 目标定位 |
|---|---|---|
| 企业级全栈 | Java、Spring Boot、Vue 3 | 面向企业级业务系统与微服务架构 |
| 智能与数据 | Python、FastAPI、PyTorch | 面向数据处理、自动化脚本与智能体工程 |

### 阶段四：系统与数据底层

掌握 Linux 基础命令、文件系统权限与网络通信原理，理解服务端程序的运行环境。

学习 MySQL 关系型数据库，掌握数据表设计、索引原理与常用 SQL 查询语法。

### 阶段五：工程化项目与实战

接入真实业务项目或学科竞赛，参与需求分析、接口联调与模块交付。

遵循基础先行、理解驱动原则，在掌握底层原理与框架逻辑的前提下，合理使用编程 Agent 辅助开发，提升编码与调试效率。

### 学习协作机制

高年级成员提供日常答疑与代码辅导。

每个阶段任务完成后进行一对一代码审查，重点评估代码结构、面向对象规范与健壮性。

## 2. 环境与工具 · `env-setup`

**摘要**：开发工具选型、运行时矩阵与工程配置原理。
**阅读**：4 分钟

### 编辑器与集成开发环境

选择适合自身技术栈的开发工具：

| 工具 | 类型 | 适用场景 |
|---|---|---|
| JetBrains（IDEA / CLion / PyCharm） | 深度集成 IDE | 适合 Java、C/C++ 与 Python 的大型项目开发与复杂调试 |
| VS Code | 插件化通用编辑器 | 适合前端全栈开发与跨语言轻量级脚本编写 |
| Zed | 高性能原生编辑器 | 适合追求低延迟响应与高效多文件编辑场景 |

### 运行时环境矩阵

项目基线环境版本：

| 运行时 | 推荐版本 | 说明 |
|---|---|---|
| Node.js | 22 LTS | 前端工程与构建工具依赖 |
| Java | 21 LTS（Temurin） | 后端微服务与企业级工程底座 |
| Python | 3.12+ | 脚本、数据处理与接口服务 |
| MySQL | 8.0+ | 关系型数据库存储 |
| Git | 2.40+ | 分布式版本控制 |

### 依赖管理与 Lockfile 机制

包管理工具通过锁文件固化项目依赖树的精确版本：

```bash
npm ci                              # 严格依据 lockfile 安装，保持环境一致
npm install                         # 会解析并可能更新依赖版本，仅在新增依赖时使用
```

在多人协同或持续集成流水线中，统一使用 `npm ci` 避免因依赖版本漂移导致构建不一致。

### 跨平台换行符处理

Windows 默认使用 CRLF 作为换行符，Unix/Linux 与 macOS 使用 LF。跨系统协作时，不同换行符会导致 Git 产生大面积无意义的代码变更。

在本地关闭自动转换，并通过仓库的 `.gitattributes` 统一声明文件换行规则为 LF：

```bash
git config --global core.autocrlf false
```

### 环境变量与配置隔离

从模板文件 `.env.example` 复制生成本地配置文件 `.env.local`。

`.env.local` 属于本地私有配置，必须包含在 `.gitignore` 中，严禁将密码、Token、密钥与内网地址提交至版本库。

## 3. 第一周 · `first-week`

**摘要**：新成员前七天的核心任务与协作习惯。
**阅读**：3 分钟

### 前三天：项目熟悉

跑通一个项目的本地构建与启动流程，阅读仓库的 `README` 与目录结构。

理清前后端模块的职责边界与配置文件的作用。

### 第四至五天：方案梳理与初次编码

认领标有 `good first issue` 的入门任务，首个提交控制在 50 行代码以内。

编码前在对应 issue 下方简要陈述修改方案与预期效果，确认思路无误后再进行修改。

### 第六至七天：测试与提交

为修改的代码补充对应的单元测试用例，覆盖核心分支。

运行本地完整质量检查，确认无报错后再发起合并请求：

```bash
npm run typecheck && npm run test && npm run build
```

### 问题排查与提问方式

遇到问题先检索仓库历史提交与 issue 讨论记录。

寻求协助时提供完整的报错堆栈、环境信息与复现步骤，准确描述预期行为与实际表现。

# 约定

## 4. 分支与提交 · `git-flow`

**摘要**：分支命名、原子提交规范与 PR 流转。
**阅读**：3 分钟

### Git 状态模型

文件在工作区进行编辑修改，通过 `git add` 暂存至暂存区，通过 `git commit` 生成版本记录，最后推送到远程仓库。

### 分支管理

分支命名规范：

```
feat/<简短英文>      新功能开发
fix/<简短英文>       缺陷修复
chore/<简短英文>     依赖与构建配置更新
docs/<简短英文>      文档更新
```

从 `main` 主分支检出新分支进行开发，完成后发起合并请求，严禁直接向主分支推送代码。

### 提交记录规范

遵循小步多次提交原则，禁止在开发最后阶段一次性提交全量代码。

提交信息采用 Conventional Commits 格式，清晰表述变更意图：

```
feat(auth): 增加用户登录参数校验
fix(table): 修复移动端列表数据溢出
```

### 合并请求流程

合并请求说明需包含三项内容：改动内容、改动原因、验证方式。

涉及界面调整时附带截图，截图前需对真实姓名、学号等敏感数据进行脱敏处理。

严禁在团队共享分支执行强制推送（force push）。

## 5. 前端约定 · `frontend`

**摘要**：TypeScript 类型约束、样式令牌、状态管理与组件设计。
**阅读**：4 分钟

### TypeScript 类型约束

启用 `strict: true` 严格模式。

避免使用 `any` 类型，无法推断类型时使用 `unknown` 并通过条件守卫收窄类型。

对外暴露的公共函数与接口必须显式标注返回类型。

### 目录与单一真源

前端目录架构划分：

```
src/
  components/    通用可复用组件，不耦合具体业务
  sections/      页面独立区块
  data/          静态数据与配置常量
  lib/           纯函数工具库
  styles/        全局样式与设计令牌
```

同一数据或常量仅在一处定义，跨模块使用时通过引用引入，禁止复制代码片段。

### 设计系统与样式变量

颜色、字体尺寸、间距与圆角统一采用 CSS 变量管理，禁止在组件中硬编码十六进制色值与数值：

```css
/* 推荐 */
color: var(--sky-500);
padding: var(--space-3);

/* 避免 */
color: #2e9be0;
padding: 12px;
```

### 状态管理与路由下沉

页面检索条件、分页参数与筛选标签等状态优先下沉至 URL Query String，确保页面刷新后状态可复原。

仅在跨多层组件传递共享数据时使用 Context，避免创建不必要的全局 Store。

### 交互组件设计考量

组件设计需契合业务场景：以轮播图为例，在品牌官网适合作为首页主视觉，在电商页面适合用于商品详情多图切换，在管理后台则应保持克制，避免遮挡核心数据区域。

页面动效优先限制在 `transform` 与 `opacity` 属性，且必须支持在系统开启减弱动态效果时自动降级。

## 6. 后端约定 · `backend`

**摘要**：分层架构、面向对象设计、文件持久化与健壮性。
**阅读**：4 分钟

### 服务端分层架构

服务端应用分为控制层、业务逻辑层与数据访问层：

```
controller   负责请求接收、参数校验与协议组装
service      负责业务规则执行与事务边界管理
mapper       负责数据库访问与持久化操作
```

控制层不得直接注入数据访问层，事务注解统一声明在业务方法上。

### 面向对象与业务解耦

实体类承载数据状态，业务计算逻辑由独立的业务服务承载。

针对多规则排序或策略切换场景，通过比较器接口或策略模式将算法实现与业务对象解耦。

### 文件 I/O 与数据持久化

本地文件持久化需定义清晰的结构化格式，使用固定分隔符或标识符区分字段，禁止直接将对象转为无格式文本存储。

文件读取逻辑需具备容错机制，在文件不存在或数据格式损坏时提供安全兜底，避免程序崩溃。

### 业务异常与统一拦截

业务失败时主动抛出携带错误码的自定义业务异常。

在外围配置全局异常处理器，将异常集中转换为统一的错误响应格式，避免直接暴露底层堆栈。

### 结构化操作日志

对数据增删改等核心操作输出结构化日志，记录时间、操作人、业务类型与执行结果。

日志统一以追加模式写入；严禁在日志中记录明文密码与密钥，手机号等敏感信息需进行脱敏处理。

# 质量

## 7. 接口与数据 · `api-contract`

**摘要**：OpenAPI 契约生成、统一响应结构与 SQL 数据设计。
**阅读**：4 分钟

### 契约驱动与类型生成

服务端定义并导出 OpenAPI 规范文档，前端通过代码生成工具自动生成 TypeScript 类型定义与请求方法，避免手动维护接口契约。

### 统一响应与分页协议

接口响应采用统一包装结构：

```ts
interface ApiResponse<T> {
  code: number
  message: string
  data: T
}

interface Page<T> {
  items: T[]
  total: number
  page: number
  size: number
}
```

业务状态码 `code` 为 0 表示操作成功，传输层 HTTP 状态码与业务状态码分工明确。分页查询的每页容量由服务端设置最大上限强制截断。

### 数据库模型设计

SQL 语言涵盖数据定义（DDL）、数据操作（DML）与数据查询（DQL）。

数据表必须具备主键约束，外键关联字段需保持类型一致，核心字段明确标注非空约束并设定合理默认值。

数据库表结构变更统一采用版本化数据库迁移工具进行管理。

### SQL 查询与数据安全

多表关联查询应基于索引字段进行连接，避免在大表上执行无索引全表扫描。

数据访问层必须使用参数化查询或预编译语句，严禁直接拼接 SQL 字符串，杜绝 SQL 注入风险。

## 8. 测试与评审 · `testing`

**摘要**：核心测试范围、自动化门禁与代码评审标准。
**阅读**：3 分钟

### 测试范围划分

核心计算逻辑、权限判定、状态机状态跃迁、外部输入解析以及历史缺陷修复必须编写测试用例。

避免对框架底层行为、无分支的简单透传方法进行无意义的测试堆砌。

### 单元测试编写规范

单个测试用例专注于验证一个具体行为，用例命名应清晰表达前置条件与预期结果：

```ts
it('参数为空时返回校验失败异常', () => {
  // 执行测试逻辑与断言
})
```

### 本地门禁流水线

提交代码或发起合并请求前，必须在本地完整运行质量门禁：

```bash
npm run typecheck && npm run lint && npm run test
```

任何检查未通过的代码不得提交至远程仓库。

### 代码评审核心维度

评审聚焦四项核心要素：运行正确性（边界与空值处理）、接口兼容性（是否存在破坏性变更）、代码可读性（命名与结构是否清晰）、架构分层（职责是否清晰）。

格式化与基础代码风格交由自动化工具处理，评审意见需清晰区分必须修改项与建议项。
