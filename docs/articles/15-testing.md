### 测试金字塔与重点覆盖范围

团队推行轻量、高效的质量保证体系，将有限的测试精力聚焦于核心高价值区域：

```
       / \
      / E2E \       端到端测试：覆盖核心冒烟路径与主流程闭环
     / 集成测试 \     集成测试：覆盖服务接口、数据库事务与第三方集成
    / 单元测试   \   单元测试：覆盖核心计算、边界校验与复杂业务算法
```

业务逻辑中的核心计算公式（如折现算法、矩阵运算、权限判定）与数据解析器属于高风险模块，必须具备完备的单元测试用例覆盖。

### 单元测试设计与行为命名规范

测试用例编写遵循行为驱动与清晰表述原则，推荐采用 Given-When-Then 或 Should-When 命名模式：

```ts
// 推荐的单测命名格式：明确前置条件、触发动作与预期结果
test('应当在优惠券有效且满足门槛时正确计算折后总价', () => {
  // Given: 准备订单金额与有效优惠券
  // When: 执行计价逻辑
  // Then: 断言返回金额精确符合折扣预期
})
```

测试用例应保持独立性与幂等性，避免依赖外部不可控的真实网络接口，推荐通过 Mock 模拟外部依赖。

### 本地质量门禁与流水线验证

在发起合并请求之前，开发者应在本地执行完整的质量检验流水线：

```bash
# 本地门禁检验三步法
npm run typecheck    # 1. 静态类型严格检查
npm test             # 2. 自动化单元测试套件
npm run build        # 3. 生产打包与预渲染构建验证
```

### 代码评审四大核心维度

代码评审（Code Review）是保障工程质量与促进经验交流的关键环节。评审过程中重点关注以下四大维度：

| 维度 | 审查关注点 | 典型排查项 |
|---|---|---|
| 正确性 | 边界条件、空指针防范与异常兜底 | 集合是否可能为空、除数是否可能为零、事务回滚边界 |
| 可读性 | 命名语义清晰、职责单一与模块解耦 | 变量命名是否自解释、函数长度是否适中、有无冗余死代码 |
| 安全性 | 参数化防注入、权限校验与数据脱敏 | 是否存在 SQL 拼接、越权访问隐患、日志有无泄露密码 |
| 性能与规范 | 索引命中、内存管理与资源释放 | 是否存在 N+1 查询、流对象是否安全关闭、组件有无内存泄漏 |
