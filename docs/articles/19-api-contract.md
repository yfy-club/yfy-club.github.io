### 核心背景与技术定位

前后端联调的经典灾难是「各写各的」：前端按口头约定写调用，后端按自己的理解实现，联调当天互相甩锅。契约优先的原则是把接口定义变成一份双方共同生成的源头文件——契约是法律，代码只是执法。

#### 契约优先的三个收益

一是消灭手抄：类型与请求客户端从契约生成，字段改名两端同步报错。二是提前暴露分歧：契约评审在编码之前，字段语义、错误码语义先吵完再动手。三是文档永生：接口文档就是契约文件本身，不存在「文档没跟上代码」。

### OpenAPI 驱动的契约流水线

#### 契约文件是唯一真源

接口以 OpenAPI 3.0 文件定义，包含路径、方法、请求体、响应体与错误响应。评审通过后，流水线向两端同时生成产物：

```bash
# 前端侧：从契约生成 TypeScript 类型与请求客户端
npx openapi-typescript openapi.yaml -o src/api/schema.d.ts

# 后端侧：从契约生成接口骨架，实现类只写业务不写签名
# （以项目使用的生成器为准，产物同样纳入版本控制）
```

生成的文件带「由契约生成，勿手改」的头注，纳入类型检查门禁——谁手改生成文件，谁在下次生成时自食其果。

#### 契约变更的评审纪律

契约合入主干后才算生效；任何字段新增、改名、删除都必须走合并请求评审，破坏性变更（删字段、改类型）必须升版本号并通知全部调用方。禁止「先改代码后补契约」——那等于回到了口头约定时代。

### 统一响应协议与错误码映射

#### 传输层与业务层的双层协议

HTTP 状态码描述传输层事实，响应体里的业务错误码描述业务层事实，两层各司其职、不可互相替代：

| HTTP 状态码 | 传输层语义 | 业务层错误码示例 |
|---|---|---|
| 200 | 请求成功送达并被处理 | `0` 成功，非 0 为业务失败 |
| 400 | 请求参数不合法 | `1001` 参数校验失败 |
| 401 | 未认证或令牌过期 | `1002` 令牌失效需重登 |
| 403 | 已认证但无权限 | `1003` 权限不足 |
| 404 | 资源路径不存在 | `1004` 目标记录不存在 |
| 500 | 服务端内部故障 | `1005` 服务内部错误 |

#### 统一响应包装

所有接口响应遵循同一个信封结构，前端拦截器按统一逻辑解包：

```json
{
  "code": 0,
  "message": "ok",
  "data": { "id": 42, "name": "示例记录" }
}
```

`code` 为 0 时读 `data`，非 0 时按错误码分支处理；`message` 永远只用于展示，不允许前端解析它的文案做逻辑判断。

### 分页保护与安全防线

#### 单页容量硬上限

列表接口必须限制单页大小，前端传多少信多少等于把内存与数据库交给运气。社团约定：默认每页 20 条，硬上限 100 条，超限直接回落到上限值并在响应中明示：

```ts
// 服务端分页参数防御：任何来自请求的分页值都先过这里
export function sanitizePage(raw: unknown, rawSize: unknown) {
  const page = Number(raw)
  const size = Number(rawSize)
  return {
    page: Number.isInteger(page) && page > 0 ? page : 1,
    // 硬上限 100：防全表加载拖垮内存与数据库
    size: Number.isInteger(size) && size > 0 ? Math.min(size, 100) : 20,
  }
}
```

#### 深分页的游标方案

`LIMIT 100000, 20` 式的偏移分页在深页会扫描并丢弃十万行，数据库压力随页码线性恶化。大结果集的遍历与导出改用游标：以上一页最后一条的主键作为下一页起点，配合单页上限循环取数直到取空。

```sql
-- 游标分页：起点是上一页最后一行的主键，扫描量恒定
SELECT id, name, score FROM student
WHERE id > 86000
ORDER BY id
LIMIT 100;
```

SQL 注入至今仍在高危漏洞榜前列，根因只有一个：把用户输入拼进了 SQL 文本。社团铁律——**全量参数化，零拼接**：

```java
// 反例：字符串拼接——输入 1' OR '1'='1 即可拖走全表
String sql = "SELECT * FROM student WHERE name = '" + name + "'"; // 禁止

// 正例：预编译语句，参数只作为数据永远不会被解释为指令
public Student findByName(String name) {
    if (name == null || name.isBlank()) {
        return null; // 空值防御在 SQL 之前
    }
    String sql = "SELECT id, name FROM student WHERE name = ?";
    return jdbcTemplate.queryForObject(
        sql, (rs, rowNum) -> new Student(rs.getLong("id"), rs.getString("name")), name);
}
```

排序字段等无法参数化的位置，用白名单校验枚举值后再拼接，白名单之外的输入直接拒绝。代码评审对字符串拼接 SQL 零容忍，静态扫描工具同时纳入门禁。

### 高频故障与实操避坑

| 症状 | 根因 | 修复方案 |
|---|---|---|
| 联调字段对不上 | 没有契约或契约未更新 | 契约先行，生成物入仓，门禁校验 |
| 列表接口拖垮服务 | 分页大小不设防 | 硬上限 + 默认值回落 |
| 深页越翻越慢 | 偏移分页线性扫描 | 改游标分页 |
| 前端解析文案做判断 | 错误语义绑在 message 上 | 逻辑分支只认错误码 |
| 排序参数被注入 | 排序字段直接拼接 | 白名单枚举校验 |

### 实操验收清单

| 项目 | 验收标准 |
|---|---|
| 契约真源 | 全部接口在 OpenAPI 文件中有定义，生成物与契约一致 |
| 协议一致 | 全部接口走统一信封结构，错误码表收录在契约内 |
| 分页保护 | 超限分页请求被回落，无全表加载路径 |
| 注入防线 | 静态扫描无 SQL 拼接；抽测注入载荷全部被参数化挡住 |
| 版本纪律 | 破坏性变更有版本号与调用方通知记录 |
