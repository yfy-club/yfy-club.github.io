### OpenAPI 契约驱动与类型生成

推荐采用契约优先（Contract-First）的设计理念：

在前后端联调前先对齐并定义 OpenAPI 3.0 接口规范。前端可通过自动化脚本根据 OpenAPI 定义直接生成类型安全的 TypeScript 接口定义与请求客户端，从根源消除前后端字段命名与类型不一致的问题。

### 统一响应协议与状态码映射

接口返回统一包装结构，明确区分传输层与业务层状态：

```json
{
  "code": 0,
  "message": "success",
  "data": { ... },
  "timestamp": 1700000000000
}
```

* **HTTP 传输状态码**：200（成功）、400（参数校验失败）、401（未登录）、403（无权限）、404（资源不存在）、500（服务器内部异常）；
* **业务错误码**：在 HTTP 状态码为 200 或业务失败时，通过 `code` 提供细分业务含义（如 `100101: 账号已被冻结`）。

### 分页查询设计与上限保护

分页查询接口统一采用标准化参数：当前页码（`page`）与每页条数（`pageSize`）。

服务端必须对 `pageSize` 设置硬性上限约束（如单页最多不超过 100 条），防止客户端恶意请求超大分页导致数据库全表加载与内存溢出（OOM）。

### 数据库实体约束与模型设计

表结构设计必须具备严密的数据完整性约束：

* **主键规范**：每张表必须包含自增主键或分布式唯一 ID（如雪花算法）；
* **自然唯一键**：业务唯一标识（如用户名、工号、邮箱）必须建立唯一索引（`UNIQUE INDEX`）；
* **非空约束**：关键字段设定 `NOT NULL` 并指定合理的默认值，减少空指针与三值逻辑判断。

### 参数化查询与安全防注入

数据持久层统一使用参数化查询（Parameterized Queries）或 PreparedStatement 预编译语句。

严禁将客户端传入的未过滤字符串直接拼接进 SQL 查询语句中，确保输入参数仅作为字面量参与运算，彻底防范 SQL 注入攻击。
