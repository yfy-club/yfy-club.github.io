### 核心背景与技术定位

前五个阶段的能力都在「个人可控」的环境里练习，阶段六要把它们放进真实的多人与多系统环境：别人会改你的代码，流水线会否决你的提交，用户会触发你没想到的路径。本阶段以社团自研项目（智学伴、智光耀城、矩阵计算器）与学科竞赛为靶场，完成从「会写代码」到「能交付」的跨越。

#### 为什么真实项目无法被教程替代

教程的环境是裁剪过的：依赖版本已知、接口文档齐全、没有人跟你抢同一个文件。真实项目的每一个变量都在动——需求会变更、依赖会破坏性升级、并发请求会暴露你在单机上永远测不出的问题。这些「动」才是工程能力的磨刀石。

### 现代工程协同基础设施

#### CI 门禁流水线

社团项目的每次合并请求都要过自动化门禁，典型配置把类型检查、单元测试与构建串成一条不可跳过的链：

```json
{
  "name": "门禁流水线",
  "on": { "pull_request": { "branches": ["main"] } },
  "jobs": {
    "check": {
      "steps": [
        { "run": "npm ci" },
        { "run": "npm run typecheck" },
        { "run": "npm test" },
        { "run": "npm run build" }
      ]
    }
  }
}
```

门禁的意义在于把「人不好意思提的意见」交给机器说：类型不通过、测试变红、构建失败，合并按钮自动锁死。人只做机器做不了的审查——设计是否合理、命名是否达意、边界是否想全。

#### 分支协同与提交纪律

多人并行的基础是分支隔离：每人从最新主干检出特性分支，小步提交，尽早发起合并请求暴露冲突。具体的分支命名与提交规范见《分支管理与提交规范》篇，这里只强调一点：**主干永远可发布**，任何破坏主干的提交都要在当天复盘。

#### 静态质量度量

类型检查与 Lint 是第一道，此外项目级门禁还包括：单测覆盖率阈值、依赖漏洞扫描、提交信息格式校验。度量不是为了分数，而是让「质量」从形容词变成可以回退定位的数字。

### 智能体辅助研发范式

#### AI 协作的底层哲学

社团的 AI 工程哲学有两条：**人的认知上限决定 AI 工具的产出上限**——你看不懂 AI 生成的代码，那段代码就是埋进项目的地雷；**底层先行、理解驱动**——先有体系化的底层原理，再接入 AI 辅助，顺序反了就是放大错误而不是放大效率。

#### 三个高价值协作场景

| 场景 | 用法 | 人的职责 |
|---|---|---|
| 接口设计 | 用 AI 起草 OpenAPI 契约与字段注释 | 逐条核对字段语义与错误码语义 |
| 测试用例生成 | 用 AI 批量生成边界与异常用例骨架 | 判断用例是否真覆盖业务规则 |
| 代码审查辅助 | 用 AI 初审重复代码与明显缺陷 | 终审设计决策，签字的永远是人 |

#### 反例与正例：AI 产出的两种对待

```ts
// 反例：AI 生成的代码直接合入——这个 API 在依赖库里根本不存在（幻觉），
// 类型被断言成 any 绕过检查，错误处理被一句 catch 吞掉
import { parseConfig } from 'some-lib'

export function loadConfig_bad(raw: unknown) {
  try {
    return (parseConfig as any)(raw, { strict: 'maybe' })
  } catch {
    return {} // 静默吞错：配置坏了自己都不知道
  }
}
```

```ts
// 正例：AI 草稿经人工核对后重写——API 换成真实存在的函数，
// 入参出参都有类型，失败路径快速失败并给出上下文
export interface AppConfig {
  readonly apiUrl: string
  readonly timeoutMs: number
}

export function loadConfig_good(raw: string): AppConfig {
  if (!raw.trim()) {
    throw new Error('配置内容为空，请检查配置来源')
  }
  const parsed: unknown = JSON.parse(raw)
  if (typeof parsed !== 'object' || parsed === null) {
    throw new Error('配置根节点必须是对象')
  }
  const obj = parsed as Record<string, unknown>
  if (typeof obj.apiUrl !== 'string' || typeof obj.timeoutMs !== 'number') {
    throw new Error('配置缺字段：apiUrl / timeoutMs')
  }
  return { apiUrl: obj.apiUrl, timeoutMs: obj.timeoutMs }
}
```

区别不在 AI 用没用，而在**门禁过没过**：反例把 AI 当作者，正例把 AI 当实习生——产出必须过审查、过类型、过测试，才能进主干。

### 竞赛实战牵引

学科竞赛是阶段六的第二靶场：蓝桥杯与天梯赛练算法手感，数学建模练快速建模与工程落地，iCAN 与互联网+练完整产品表达。竞赛的正确打开方式是「以赛带练」：赛前按真题做针对性训练，赛中按工程纪律分工提交，赛后把可复用代码沉淀回社团仓库——荣誉是副产品，能力资产才是主产品。

### 高频故障与实操避坑

| 症状 | 根因 | 修复方案 |
|---|---|---|
| 门禁红了自己不知道 | 本地不跑检查直接推 | 推送前本地跑一遍与 CI 相同的命令 |
| AI 生成的依赖不存在 | 模型幻觉出虚构的库与 API | 逐个核对包名与版本号，只信官方文档 |
| 合并冲突连环爆 | 特性分支与主干失联太久 | 每天拉主干变基，冲突不过夜 |
| 演示环境正常、部署就挂 | 环境变量与配置漂移 | 配置一律走环境变量，部署清单写进仓库 |
| AI 生成的代码带了受限协议片段 | 未审查许可证来源 | 涉第三方代码必须标注来源与协议 |

### 阶段实战大作业与验收清单

在社团开源项目中认领一个真实特性，走完从需求到合入的全流程：

| 项目 | 验收标准 |
|---|---|
| 需求分析 | 产出需求说明：改什么、为什么改、影响哪些模块 |
| 接口设计 | 涉及接口的先出 OpenAPI 契约，评审通过后再编码 |
| 编码测试 | 特性代码带单元测试，本地与 CI 门禁全绿 |
| 合并请求 | 描述含改动内容、原因与验证方式，评审意见全部销项 |
| AI 使用记录 | 说明哪些部分借助了 AI，以及人工核对与修改了什么 |
| 复盘沉淀 | 合入后输出一段复盘：最大的返工点与下次怎么避免 |
