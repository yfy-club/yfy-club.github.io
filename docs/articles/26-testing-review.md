### 核心背景与技术定位

质量的最后一道防线只有两层：机器跑的测试与人做的评审。测试负责证明「代码按设想工作」，评审负责追问「设想本身对不对」。本篇给出社团对这两层防线的量化标准——测什么、怎么隔离、覆盖率门禁多少、评审按哪二十项核对。

#### 测试金字塔的社团裁剪

单元测试是绝对主力：快、稳、可定位，覆盖核心业务逻辑的全部路径。集成测试只补关键链路（如事务与持久化），端到端测试只守最关键的用户路径。倒金字塔（大量端到端、极少单测）的团队，测试跑得慢、失败定位难，最终的下场是没人再跑测试。

### 单元测试纪律：隔离、打桩与覆盖率

#### 隔离原则

单元测试的铁律是**只测一个单元**：不碰数据库、不碰网络、不碰文件系统、不依赖执行顺序。凡是跨越进程边界的东西，一律用桩替代——这不是偷懒，而是让测试可以在任何机器上以任何顺序毫秒级跑完的前提。

#### 打桩模拟的两种姿势

```ts
// 前端侧（Vitest）：网络请求打桩，断言组件对两种结果的处理
import { vi } from 'vitest'

vi.mock('../api/client', () => ({
  fetchCourses: vi.fn(),
}))

// 成功路径断言渲染结果
// 失败路径断言降级提示——失败分支不测等于没测
```

```java
// 后端侧（Mockito）：Mapper 打桩，只验证 Service 的业务决策
@Test
void register_nameTaken_throwsBiz() {
    when(userMapper.existsByName("张三")).thenReturn(true);

    assertThatThrownBy(() -> service.register(dtoOf("张三")))
        .isInstanceOf(BizException.class)
        .hasMessageContaining("已存在");
    verify(userMapper, never()).insert(any()); // 重复名必须不落库
}
```

#### 边界断言的清单意识

每个被测方法至少覆盖三类断言：正常路径的期望输出、边界输入（空、零、上限、临界值）、异常路径的抛出与副作用。写测试先列边界清单再动手，是区分「测过」和「测到」的分水岭。

覆盖率是下限不是目标：100% 覆盖率挡不住断言写反的测试，但没有覆盖率门禁，核心代码必然裸奔。社团门禁指标：

| 范围 | 行覆盖率 | 分支覆盖率 |
|---|---|---|
| 核心业务逻辑（Service 层） | 不低于 80% | 不低于 70% |
| 工具与转换模块 | 不低于 90% | 不低于 80% |
| 控制器与配置类 | 不强制 | 不强制 |

覆盖率报告纳入门禁流水线，下降即红；为凑覆盖率而写的无断言测试（只调用不断言）在评审中按无效测试处理。

### 代码评审二十项核对清单

评审人按四组逐项核对，任何一项命中都要给出意见：

| 组 | 核对项 |
|---|---|
| 空值防御 | 外部入参判空 / 集合取值判空 / 可空返回有兜底 / 解引用前收窄 / 配置缺失有默认 |
| 并发安全 | 共享可变状态加锁 / 并发容器选型正确 / 无竞态的复合操作 / 锁范围最小化 / 异步回调线程安全 |
| 事务边界 | 事务注解在 Service 层 / 异常触发回滚声明 / 无同类自调用 / 长事务已拆分 / 事务内无外部调用 |
| 资源关闭 | 流与连接用 try-with-resources / 监听器有注销 / 定时器有清理 / 锁有释放路径 / 大对象及时置空 |
| 类型断言 | 无 as any 与强转逃逸 / 反序列化先校验 / 枚举转换有未知分支 / 数值范围已检查 / 泛型约束已收紧 |

#### 评审的礼仪与纪律

意见对事不对人，描述问题与建议而不是评判作者；作者逐条销项，不同意的当面讨论不留暗账。评审时长单次不超过一小时，改动超过四百行先拆再审——评审人对着千行改动只能给出「看起来没问题」这种无效结论。

### 正反例设计范式

#### 反例：无断言的假测试与耦合环境的慢测试

```ts
// 反例一：只调用不断言——覆盖率涨了，问题一个都拦不住
it('假测试', () => {
  parseConfig('{"a":1}')
})

// 反例二：直连真实接口——网络一抖全红，从此没人再跑
it('慢测试', async () => {
  const data = await fetch('https://api.example.com/courses')
  expect(data.status).toBe(200)
})
```

#### 正例：边界清单驱动的隔离测试

```ts
// 正例：纯函数直接断言边界；外部依赖全部打桩
it('分页参数超上限回落到 100', () => {
  expect(sanitizePage('1', '99999')).toEqual({ page: 1, size: 100 })
})

it('非法页码回落第一页', () => {
  expect(sanitizePage('-3', 'abc')).toEqual({ page: 1, size: 20 })
})

it('空配置快速失败', () => {
  expect(() => loadConfig('   ')).toThrow('配置内容为空')
})
```

### 高频故障与实操避坑

| 症状 | 根因 | 修复方案 |
|---|---|---|
| 测试时绿时红 | 依赖时间、顺序或真实环境 | 打桩隔离，固定测试时钟 |
| 改了 A 红了 B | 测试间共享可变状态 | 每用例独立初始化，禁止全局变量 |
| 覆盖率高但事故照发 | 断言只测成功路径 | 评审测试代码本身，补边界与异常断言 |
| 评审走过场 | 改动过大评审疲劳 | 拆分请求，单次评审限四百行 |

### 实操验收清单

| 项目 | 验收标准 |
|---|---|
| 隔离性 | 断网断库环境下全量测试通过，执行顺序打乱仍通过 |
| 覆盖率 | 核心业务行覆盖与分支覆盖达标，报告入仓 |
| 断言质量 | 抽查十个用例均有明确断言，含边界与异常路径 |
| 评审记录 | 近期合并请求均有评审意见与销项记录 |
| 清单执行 | 评审意见可追溯到二十项清单的具体条目 |
