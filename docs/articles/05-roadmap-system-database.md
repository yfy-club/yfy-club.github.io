### 核心背景与技术定位

后端服务从写下的第一天起就运行在 Linux 上、把数据落在 MySQL 里。不会 Linux，部署排障全依赖别人；不懂存储引擎，慢查询只会盲目加索引碰运气。本阶段把「系统底座」与「数据基座」一次打齐，是阶段五企业级开发的前置条件。

#### 为什么先原理后命令

Linux 命令与 SQL 语法都容易速成，但真正拉开差距的是原理：权限位怎么读、服务为什么起不来、索引为什么没生效。本阶段每学一组命令，都要落到「它改动了系统的哪个状态」，拒绝无理解的复制粘贴。

### Linux 系统底座实操

#### 用户权限体系

文件权限以三组三位的结构表达：属主、属组、其他人各占读（r=4）、写（w=2）、执行（x=1）三位。`-rw-r--r--` 即 644：属主可读写，其余人只读。生产纪律：应用进程一律用低权限专属用户运行，禁止 root 直跑；密钥文件收敛到 600。

```bash
# 查看权限与属主，确认服务账号与密钥位是否符合基线
ls -l /opt/app/app.jar

# 授权目录给服务账号，避免用 777 这种彻底放权的写法
sudo chown -R appuser:appgroup /opt/app
chmod 750 /opt/app
chmod 600 /opt/app/.env   # 含密钥的配置文件必须只有属主可读

# 切换服务账号验证权限最小化是否成立
sudo -u appuser whoami
```

#### systemd 服务管理

生产服务一律注册为 `systemd` 单元，获得开机自启、崩溃拉起与统一日志三件套。核心命令四件：`systemctl start|stop|restart|status 服务名`；排障先看 `systemctl status` 的最近日志，再看 `journalctl -u 服务名 -n 100` 的全量输出。

#### 进程与资源排查三板斧

| 工具 | 回答的问题 | 常用姿势 |
|---|---|---|
| `top` | 谁在吃 CPU 与内存 | 按 `M` 按内存排序，盯 `load average` |
| `ps` | 进程在不在、以谁的身份在跑 | `ps -ef | grep java` |
| `ss` | 端口被谁监听、连接堵在哪 | `ss -lntp` 看监听 |

### InnoDB 索引与 B+ 树底层

#### 为什么是 B+ 树

数据库索引要解决的是「磁盘上千万行里快速定位」的问题。B+ 树是多路平衡查找树：一个节点占一个磁盘页（16KB），扇出极大，三层树高即可索引两千万行级别的表，定位一行最多三次磁盘 IO。B+ 树相比 B 树的关键差异在叶子层：**所有数据都落在叶子节点，且叶子之间以双向链表串起**——范围查询只需定位到起点，然后沿链表顺序扫描，不必回树。

#### 聚簇索引与二级索引

InnoDB 的表数据本身就按主键组织成 B+ 树，这棵树叫聚簇索引：叶子节点直接存整行数据。其他索引（二级索引）的叶子里存的不是行，而是主键值。因此走二级索引查整行要两步：先在二级索引树里拿到主键，再回聚簇索引树里按主键取行——第二步就是**回表**，它是一次完整的二次查找，回表次数多，查询就慢。

#### 覆盖索引消灭回表

如果查询需要的列恰好都在二级索引里，就不必回表，这叫覆盖索引。`EXPLAIN` 输出里出现 `Using index` 即命中。大结果集的分页与列表页查询，应优先设计覆盖索引，或改为游标式分页。

### 事务、隔离级别与并发控制

#### ACID 的实现支柱

原子性（A）靠 undo log：事务回滚时按反向日志撤销修改。持久性（D）靠 redo log：修改先写日志再刷数据页，崩溃后可重放。隔离性（I）靠锁与 MVCC 的组合。一致性（C）是前三者共同达成的业务目标。

#### 四种隔离级别与副作用

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---|---|---|---|---|
| 读未提交 | 可能 | 可能 | 可能 | 几乎不用 |
| 读已提交（RC） | 不会 | 可能 | 可能 | Oracle 默认 |
| 可重复读（RR） | 不会 | 不会 | InnoDB 基本消除 | MySQL 默认 |
| 串行化 | 不会 | 不会 | 不会 | 全加锁，并发最差 |

#### MVCC 与 Next-Key Lock

MVCC（多版本并发控制）让读不加锁：每行数据带隐藏的事务版本号与回滚指针，事务按自己的一致性视图读取历史版本，读写互不阻塞，这是 InnoDB 高并发的根基。写与写的冲突则靠锁：RR 级别下的**Next-Key Lock** 锁住记录与其前一段间隙，既防并发改同行，又堵住间隙插入造成的幻读。

### 正反例与执行计划诊断

#### 反例：三种典型索引失效写法

```sql
-- 反例一：对索引列做函数包装，索引树无法定位，全表扫描
SELECT * FROM student WHERE YEAR(create_time) = 2026;

-- 反例二：隐式类型转换，phone 是字符串列，传数字触发列上隐式转换
SELECT * FROM student WHERE phone = 13800138000;

-- 反例三：联合索引 (grade, class_id) 跳过最左列直接查 class_id
SELECT * FROM student WHERE class_id = 3;
```

隐患拆解：函数与运算让索引树的有序性失去意义；隐式类型转换等价于在列上套了转换函数；最左前缀缺失则根本没有可用的有序起点。三者的共同症状是 `EXPLAIN` 中 `type` 掉到 `ALL`，行数扫满全表。

#### 正例：可索引写法与覆盖分页

```sql
-- 正例一：范围改写成索引列裸奔的形式
SELECT * FROM student
WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01';

-- 正例二：类型严格匹配，字符串列配字符串字面量
SELECT * FROM student WHERE phone = '13800138000';

-- 正例三：深分页不用 LIMIT 100000, 20（前十万行读了又丢），
-- 改为主键游标：上一页最后一行的主键作为起点，回表量恒定
SELECT id, name, score FROM student
WHERE id > 86000 ORDER BY id LIMIT 20;
```

#### EXPLAIN 读图要点

诊断先看三列：`type` 从好到差大致为 `const > eq_ref > ref > range > index > ALL`，线上查询不允许出现 `ALL`；`key` 显示真正用到的索引，为空说明优化器放弃了索引；`Extra` 出现 `Using filesort` 或 `Using temporary` 说明有额外排序或临时表，是重点优化对象。
