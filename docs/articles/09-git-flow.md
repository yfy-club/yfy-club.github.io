### 核心背景与技术定位

版本控制是多人协作的物理定律：没有它，两人的修改无法安全交汇，事故无法回溯，发布无法挑选。Git 是社团所有仓库的统一版本控制系统，本篇规定它在社团项目中的使用纪律——对象模型是理解一切操作的钥匙，命名与提交规范是让历史可读的契约。

#### 为什么提交历史也是产品

代码是给机器执行的，提交历史是给人排障的。半年后线上出问题，`git bisect` 二分定位靠的就是一条条职责单一的提交；评审与复盘靠的也是历史。混乱的历史等于放弃了 Git 一半的价值。

### 底层对象模型与状态流转

#### Blob、Tree、Commit 三层对象

Git 的存储本质是一个内容寻址的对象数据库，只有三种核心对象：

| 对象 | 存储内容 | 类比 |
|---|---|---|
| Blob | 文件的字节内容 | 一页文档 |
| Tree | 目录结构与文件名到 Blob 的映射 | 文件夹 |
| Commit | 顶层 Tree 指针、父提交引用、作者与提交说明 | 一次快照的档案卡 |

每次提交都是一棵完整目录树的快照，而不是差异补丁——所以 Git 的分支切换与历史回退才如此之快。理解「提交是快照不是补丁」，才能理解为什么删除文件再提交不会丢失历史、为什么分支只是指向某个提交的可移动指针。

#### 四大区域的流转

```bash
# 工作区 -> 暂存区：挑选本次提交要包含的变更
git add src/feature.ts

# 暂存区 -> 本地历史：生成 Commit 对象
git commit -m "feat(auth): 增加登录参数校验"

# 本地历史 -> 远程仓库：推送提交对象
git push origin feat/login-check

# 反方向同步：远程 -> 本地历史 -> 工作区
git pull --rebase origin main
```

暂存区（Index）的存在是 Git 的精髓：它允许你把一个文件的一部分改动放进本次提交，把另一部分留给下次——这正是原子提交的操作基础。

### 分支策略与提交规范

#### 分支命名规则

| 前缀 | 用途 | 示例 |
|---|---|---|
| `feat/` | 新功能或特性开发 | `feat/login-check` |
| `fix/` | 缺陷与故障修复 | `fix/table-overflow` |
| `chore/` | 依赖升级、构建配置调整 | `chore/upgrade-vite` |
| `docs/` | 文档编写与更新 | `docs/git-flow` |

命名用短横线小写英文，简短达意，不带空格与中文。分支名会出现在提交历史与合并请求列表里，它是给人读的索引。

#### 从主干检出的纪律

所有日常开发基于最新的 `main` 检出特性分支：

```bash
# 先同步主干，再检出特性分支——基线落后是冲突的最大来源
git checkout main
git pull --rebase origin main
git checkout -b feat/login-check

# 分支存活期间，定期把主干变化变基进来，冲突不过夜
git fetch origin
git rebase origin/main
```

禁止直接向 `main` 推送；主干开启分支保护与强制评审。`git push --force` 对共享分支永久禁用——它会抹掉他人的提交，历史可追溯性不可让步。

#### 小步多次的原子纪律

一个提交只做一件事：一次修复、一个特性切片、一轮重构。判断标准是「能否用一句不含『和』的话概括」。把格式化与逻辑变更分开提交、把依赖升级与业务代码分开提交——出问题时才能精准回退某一块，而不是连坐退回。

#### 结构化提交信息

提交信息遵循 Conventional Commits：`类型(范围): 简述`，正文说明动机与影响：

```bash
# 三种典型类型示例
git commit -m "feat(auth): 增加用户登录参数格式校验"
git commit -m "fix(table): 修复移动端表格数据溢出遮挡"
git commit -m "refactor(user): 抽取通用权限校验中间件"

# 提交前自查：暂存内容是否与提交信息描述的单件事一致
git diff --cached --stat
```

类型与范围的词表保持收敛：`feat`、`fix`、`refactor`、`docs`、`chore`、`test`。生造类型等于没有类型。

### 合并请求流转与脱敏纪律

#### 合并请求三要素

发起合并请求时，描述必须回答三个问题：改动内容（做了什么）、改动原因（解决什么问题）、验证方式（怎么证明它有效）。涉及前端界面调整的，附操作录屏或前后对比截图。

```json
{
  "改动内容": "逐条列出本次合入的变更点，与提交记录对应",
  "改动原因": "关联的需求、缺陷单或技术债说明",
  "验证方式": [
    "本地执行的检查命令与结果",
    "新增或修改的测试用例说明",
    "界面变更附操作录屏或前后对比截图"
  ],
  "影响范围": "列出可能受影响的模块与调用方",
  "风险与回退": "上线风险点说明与回退方案"
}
```

#### 敏感数据脱敏

截图、录屏与日志在进入评审视野前必须脱敏：真实姓名、学号、手机号、令牌与线上密钥一律遮挡或替换为示例值。密钥类信息一旦进了提交历史，就要按「立即作废轮换」处理，而不是简单删文件——Git 的历史里它还活着。

#### 误提交的紧急止血

```bash
# 文件已提交但未推送：改写最近一次提交，把误加文件移出暂存
git reset --soft HEAD~1
git restore --staged .env
git commit -m "feat(auth): 增加登录参数校验"

# 已推送的密钥：先作废轮换密钥，再从历史清除，并通知所有协作者重新克隆
git filter-repo --path .env --invert-paths
```

### 高频故障与实操避坑

| 症状 | 根因 | 修复方案 |
|---|---|---|
| 变基冲突连环爆 | 分支长期未同步主干 | 每天 `git pull --rebase origin main`，冲突不过夜 |
| 提交信息牛头不对马嘴 | 一次提交混了多件事 | 用暂存区分批提交，写前先看 `git diff --cached` |
| 合并请求无人敢审 | 描述空、改动大 | 拆小：一个请求不超过四百行改动 |
| 历史里夹着大文件 | 二进制产物进了仓库 | 产物进 `.gitignore`，已入库的用 `filter-repo` 清除 |
| `detached HEAD` 提交丢失 | 检出提交而不是分支 | 立即 `git checkout -b` 给游离提交安家 |

### 实操验收清单

| 项目 | 验收标准 |
|---|---|
| 对象模型 | 能在白板上画出 Blob、Tree、Commit 的关系与四区流转 |
| 分支纪律 | 所有改动走特性分支，命名符合前缀规则，无直推主干 |
| 提交质量 | 抽查十个提交全部单一职责，信息符合规范 |
| 合并请求 | 描述含三要素，界面改动附截图，敏感信息零暴露 |
| 应急能力 | 能独立完成误提交止血与变基冲突解决 |
